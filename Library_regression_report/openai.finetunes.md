## 5. Issues in `new` (independent of `old`)

All six below are also present in `old` (i.e. none is caused by spec v2), but they are real
inaccuracies in the `new` render vs. the library source.

1. **Closed records rendered as open.** The bala declares 28 top-level `public type X record {|…|}`.
   The `new` render emits every one of them as `type X record { … };`. Verified: source closed-record
   name set (28) minus render closed-record name set (0) = all 28, including `ConnectionConfig`,
   `CreateRunRequest`, `CreateAssistantRequest`, `CreateChatCompletionRequest`'s siblings, etc.
   (The 30 `record {|` occurrences that do appear in both renders are inline/anonymous records.)
   Effect: an LLM will believe extra fields are permitted where the library rejects them.

2. **Record-field default values dropped, and defaultable fields shown as optional.**
   `types.bal` has 62 fields with `= <default>`; the render has 0 (the 5 regex hits in the render are
   all inside the README code sample, lines 80–94). Examples:
   `decimal speed = 1.0;` → `decimal speed?;` (new line 772);
   `RunObjectTools[] tools = [];` → `RunObjectTools[] tools?;` (new line 206);
   `AssistantObjectTools[] tools = [];` → `tools?;` (new line 1658).
   This both loses the default and changes required-with-default into optional.

3. **Included-record parameter `*XQueries` is flattened AND duplicated, producing non-compiling
   Ballerina.** Source: `resource isolated function get files(map<…> headers = {}, *ListFilesQueries queries)`.
   Render: `resource function get files(map<…> headers = {}, string purpose = "", ListFilesQueries queries)`.
   The `*` is gone, the record's fields are inlined as extra defaultable params, and a required param
   follows defaultable params. Affects all 12 `*…Queries` resource functions.
   Also, the inlined query fields are given defaults (`string purpose = ""`, `int limit = 0`) that do
   not exist in the source records — `ListFilesQueries` declares `string purpose?;` with no default
   (`types.bal:2509–2512`).

4. **Broken multi-line doc comment.** `new` lines 653–654 (and `old` 595–596):
   ```
       # Enables relaxed data binding on the client side. When enabled, `nil` values are treated as optional, 
   and absent fields are handled as `nilable` types. Enabled by default.
   ```
   The continuation line lost its `#` prefix and its indentation, so it reads as a stray statement.

5. **`isolated` qualifier dropped everywhere.** `grep -c isolated` → 0 in both renders, while the
   source declares `public isolated client class Client`, `public isolated function init`, and 68
   `resource isolated function` / `remote isolated function`.

6. **Open-record rest-field signal for the 12 `…Queries` records is no longer represented.**
   Those records are open (`record { … }`), so extra query params are permitted. `old` conveyed this
   (badly) as `anydata Additional Values`; `new` drops it entirely. This is information loss relative
   to `old`, but `old`'s form was non-compiling and read as a required positional parameter named
   with a space, which is more misleading than silence. Not counted as a regression.

tool, and `new` now renders all 293 of them.

## 8. Other considerations

- **Not deprecated.** Central `deprecated = None`, `deprecateMessage` empty. `graalvmCompatible = Yes`,
  `ballerinaVersion 2201.12.2`, `pullCount 46`.
- **Stable major version** (3.0.0), so no pre-1.0 volatility caveat.
- The 7 `@deprecated` markers are field/type-level OpenAI deprecations (legacy `functions` /
  `function_call` chat API), correctly preserved on both sides.
- **Size/token impact**: +295 lines (+9.7%). The 281 `@jsondata:Name` annotations account for 85% of
  the growth. This is a worthwhile trade: without them an LLM cannot know that `topP` serialises as
  `top_p`, `responseFormat` as `response_format`, etc., which is the single most common source of
  broken generated code for OpenAI-shaped connectors. `old` gave no way to recover this.
- The library is a large flat OpenAPI-generated surface (237 types, 68 operations) that mirrors the
  whole OpenAI API, not just fine-tuning; the render reflects that faithfully.
- Both renders are illustrative, not compilable, because of the issues in §5 (open records, missing
  `*`, required-after-defaultable params). `new` is closer to compilable than `old` but still not
  there.

## 10. Caveats and unverified items

- Ballerina Central's `docs/README.md` inside the bala was not byte-diffed against the render's
  README block; the render's `readme` field is identical (4347 chars) on both sides, so no
  old-vs-new question arises, but "render README == published README" is **unverified**.
- Rendered code was not compiled. The non-compiling claims in §5 (open records, missing `*`,
  required-param-after-defaultable) are based on reading the Ballerina spec rules and comparing to
  source, not on running `bal build`.
- The `record {|` counting used a textual regex; the 30 vs 32 gap is attributed to inline/anonymous
  records, which was inferred from the closed-record name-set comparison (28 top-level closed types,
  0 rendered closed) rather than from a parse.
- Only 12 of the 237 typeDefs were compared field-by-field against source; the remaining 225 were
  verified through the aggregate checks (name-set equality, annotation-pair equality, declaration-set
  equality, `@deprecated` anchors, doc-line count) rather than one at a time.
- The `old`-side and `new`-side ballerina-vscode commits (`eb5d81b3`, `412ba01e`) were taken from the
  brief; they were not independently re-verified in this review.
