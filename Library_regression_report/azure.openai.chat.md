## 1. Summary

Small, entirely positive delta. 13 hunks, +17/−12 lines. `new` fixes four classes of defect that
`old` had, and removes nothing:

1. The single `// Unknown type:` placeholder (`OpenAIChatCompletionMessageToolCallsItem`) is replaced
   by the real array-of-union definition, byte-for-byte matching the published source.
2. All 18 version/module-qualified type references (`ballerina/lang.int:0.0.0:Signed32`,
   `ballerinax/azure.openai.chat:4.0.0:*`) are normalised to plain, resolvable names.
3. Four annotations that `old` dropped are now emitted (`@display` on `ConnectionConfig`, three
   `@constraint:*` on `ChatCompletionsBody` fields) — all verified present in the bala source.
4. A bogus, non-parsable client parameter `anydata Additional Values` (the open-record rest
   descriptor of `CreateChatCompletionQueries`, leaked as a parameter) is gone.

No declaration is removed, no signature narrowed, no doc text lost. Type coverage is identical and
complete on both sides: all 78 public types of the default module plus the `Client` class appear in
both renders. This library has a single module (`modules/azure.openai.chat`), so there is no
submodule gap.

Residual inaccuracies remain in `new`, but every one of them is also in `old` (section 5).

## 5. Issues in `new` (independent of `old`)

All five below are present in **both** renders — they are pre-existing pipeline behaviour, not
introduced by spec v2. Listed because they still misinform an LLM reading `new`.

1. **Client resource signature misrepresents the included-record parameter.** Source
   (`client.bal:47`) is `*CreateChatCompletionQueries queries`. The render emits *both* the expanded
   field and the record parameter:
   `resource function post chat/completions(ChatCompletionsBody payload, map<string|string[]> headers = {}, AzureAIFoundryModelsApiVersion api\-version = "v1", CreateChatCompletionQueries queries) returns InlineResponse200|error;`
   An LLM would write a call passing a `CreateChatCompletionQueries` value positionally, which does
   not compile. (JSON `clients[0].functions[1].parameters` carries both entries on both sides.)
2. **Fabricated default `= "v1"` for `api-version`.** `types.bal:858` declares
   `AzureAIFoundryModelsApiVersion api\-version?;` — optional, **no default expression**. The JSON on
   both sides carries `"default": "\"v1\""`. The value is plausible (the doc says "`v1` if not
   otherwise specified", and `AzureAIFoundryModelsApiVersion` is `"v1"|"preview"`), but it is not in
   the source. Origin of the synthesised default is unverified.
3. **`queries` rendered as a non-defaulted parameter after defaulted ones.** Ballerina forbids a
   required parameter following defaulted parameters, so the emitted resource signature is not
   parsable as written.
4. **Multi-line doc comments lose the `#` prefix on continuation lines.** 149 such lines in both
   files (e.g. `new:1031` `` `v1` if not otherwise specified. ``, `new:880–881`, `new:891–893`).
   The render is therefore not valid Ballerina source overall.
5. **`public` and `isolated` qualifiers are stripped.** Source has
   `public isolated client class Client`, `public isolated function init`,
   `resource isolated function post`, and `public type X` throughout; the render emits
   `client class Client`, `function init`, `resource function post`, `type X`. Isolation is
   API-relevant information and is lost on both sides.

## 8. Other considerations

- **Not deprecated**; stable major version `4.0.0`, `distribution = "2201.12.0"`.
- **Generated connector**: `client.bal` and `types.bal` are marked "AUTO-GENERATED … by the Ballerina
  OpenAPI tool". The single operation `POST /chat/completions` is the entire API surface, so the
  render's usefulness hinges almost entirely on that one signature — which makes issues 1–3 in
  section 5 disproportionately costly for this library despite being pre-existing.
- **Size**: 1043 lines, ~40 KB — small; the +5 net lines are a negligible token cost for four
  restored annotations and one restored type definition.
- **Deprecated fields are correctly flagged**: 8 `@deprecated` markers survive in `new`
  (`user`, `functions`, `function_call`, etc.).
- The `ChatCompletionsBody` `@constraint` annotations now visible in `new` are materially useful:
  `messages` min length 1 and `safety_identifier` max length 64 are runtime-enforced by
  `ballerina/constraint`; an LLM generating code from `old` had no way to know.

## 10. Caveats and unverified items

- **Origin of the synthesised `api-version = "v1"` default is unverified.** The bala source declares
  no default for that field; the extractor emits one on both sides. Whether it is derived from the
  doc string or from the first member of the `"v1"|"preview"` union could not be determined without
  reading the extractor source, which is outside this library's scope. The mismatch against the
  library source is itself confirmed (`types.bal:858`).
- **`ballerina/http` types referenced by `ConnectionConfig` are not expanded** in either render
  (e.g. `http:BearerTokenConfig`, annotated in-render with "Special Agent Note: … FROM ballerina/http
  package"). This is cross-package behaviour of the pipeline, identical on both sides; whether the
  downstream consumer resolves them was not tested.
- **Renders were not compiled.** Claims of non-parsability in section 5 (items 3–4) come from reading
  the emitted text against Ballerina grammar rules, not from running `bal build` on the render — the
  render is a documentation artifact and is not intended to compile as-is.
- Ballerina Central registry metadata was not re-queried; the bala's `package.json` and `bala.json`
  plus the `v4.0.0` tag were treated as authoritative for org/name/version and module list, and they
  agree with the pinned version.
